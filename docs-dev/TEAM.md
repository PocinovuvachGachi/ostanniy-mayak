Над грою працюють двоє: **Claude** і **ChatGPT**. Обидва пишуть код, перевіряють роботу одне одного й пропонують ідеї.
Автор (PocinovuvachGachi) вирішує, що робимо, і має останнє слово. Усе нижче однаково для обох.

## Перед роботою
- Прочитати `CLAUDE.md` (загальні правила проєкту, не лише для Claude), `PRINCIPLES.md`, `DECISIONS.md`, `NEXT.md`.
  Постулати й погоджені рішення обов'язкові для обох; нове рішення ухвалює лише автор.
- Переглянути відкриті issues і pull requests: чи не робить уже хтось те саме.

## Хто що робить
- Кожне завдання — issue. Беручи його, став мітку **`claude`** або **`gpt`** і коментар: «Беру. Зачеплю: <модулі>».
  Одна issue — один розробник.
- Не беремо одночасно завдання, що правлять ті самі модулі (`src/js/…`). Якщо без цього ніяк — домовляємося в issue.
- Великі спільні файли (`11-data.js`, `40-render.js`, `style.css`) — правити невеликими шматками, швидко зливати.
- Без мітки — ніхто не бере. Ідеї без погодження автора («обговорити») — не беремо.

## Як вносити зміни
1. Гілка від свіжого `main`: `claude/<коротко>` або `gpt/<коротко>`. Прямо в `main` не пушимо.
2. Зміни в `src/`, тести в `tests/`, документи в `docs-dev/` (новий механізм — `ARCHITECTURE.md`).
3. `python3 build.py` і `node tests/run.js` (якщо браузерні тести локально не запускаються — хоча б `--logic`;
   повний штатний набір прожене GitHub Actions на pull request). Обсяг додаткових симуляцій — за правилами нижче.
4. Pull request у `main`: що зроблено, навіщо, як перевірити, `Closes #N`. Мова — українська.
5. **Рев'ю:** за рішенням автора від 28.11.2026 ChatGPT самостійно реалізує, перевіряє diff і запускає тести (зокрема через GitHub Actions). Незалежне рев'ю Claude/Codex корисне, але більше не є обов'язковою передумовою для погоджених змін ChatGPT. Самоперевірку не називати незалежним рев'ю.
6. **Зливає автор або ChatGPT.** Для погоджених змін ChatGPT може сам зливати PR після перевірки конкретного head SHA, актуального зеленого штатного CI, відсутності конфліктів і критичних/блокувальних дефектів. Якщо head змінився — повторно перевірити diff і CI. Не обходити захист гілки, не послаблювати тести та не зливати непогоджені дизайнерські зміни. Для документації достатньо перевірки diff і mergeability. Некритичні зауваження фіксувати в беклозі; ризики втрати прогресу, зламаних сюжетних порогів, критичних регресій чи невдалий CI виправляти до злиття. Ця домовленість замінює попередню вимогу обов'язкового незалежного рев'ю для власних PR ChatGPT.

## Обсяг тестування (погоджено автором 26.11.2026)

Пріоритет — змістовне поглиблення гри. Послідовно вдосконалюємо етапи I–V (це п'ять етапів, не десять сюжетних розділів), після них — спільний аудит, балансування й перевірка взаємодії всієї гри. Симулятор — інструмент, не мета.

- Окрема механіка: цільові тести зміненого коду та безпосередніх залежностей; за потреби мобільний інтерфейс, збереження, доступність, сюжетні пороги й критичні регресії. Збірка та штатний CI залишаються обов'язковими для змін коду. Не послаблювати наявні тести/CI заради швидкості.
- Завершення змістовного блоку: перевірка взаємодії його механік; симуляції лише в обсязі, потрібному для висновку.
- Завершення кожного етапу I–V: проходження й аудит цього етапу, його входу/виходу, доступності пропущених секретів і прямих залежностей. Не балансувати всі наступні етапи, які ще перероблятимемо.
- Завершення всіх п'яти етапів: повні проходження, різні стилі та зерна, глобальні економіка/бої/темп, переходи, збереження, оптимізація й фінальне балансування; перед релізом — повна регресія.
- Виняток: зміна наскрізної системи, формату збереження, глобальної економіки/прогресії або ознаки критичної регресії виправдовують ширшу перевірку зараз. Повні `--sim` / `--fights` не є автоматичною вимогою після кожної локальної зміни. У PR пояснювати, чому ширша перевірка потрібна, якщо її запускають.
- Некритичні проблеми поза поточним завданням — у BACKLOG.md / GitHub Issues, без самовільного розширення обсягу. Критичні блокери та ризик втрати прогресу не відкладати.
- У PR стисло звітувати: що змінилося для гравця, які залежності зачеплено, що перевірено/не перевірено, які ризики відкладено. Не вимагати доказу балансу всієї гри після окремої механіки.

Ця домовленість уточнює старі вимоги запускати повні симуляції після кожної зміни балансу чи відкриттів; для наступних ТЗ застосовувати її замість механічного повторення вимог #69.
